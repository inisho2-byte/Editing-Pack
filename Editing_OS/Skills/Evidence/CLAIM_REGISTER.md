# Editing OS Claim Register

This register records high-risk claims discovered during the handbook audit.
Until a claim is supported and promoted through an active-contract change, use
the treatment shown here.

| Topic | Historical formulation | Current treatment | Evidence needed |
|---|---|---|---|
| Caption exposure | Essential captions need a universal 700–900 ms floor | Project-default and review starting point | Reading/accessibility research applicable to language, device, size, and caption type |
| Visual refresh | Change something every 2–4 seconds | Heuristic for finding stalled regions; meaning beats control changes | Project retention comparison and content-type baseline |
| Three-second rule | Every three seconds must deliver novelty | Inspection cadence for fast shorts, not an edit command | First-party retention curves and controlled variants |
| Social loudness | Social delivery universally targets −14 LUFS | Starting profile; delivery spec controls | Current platform/client/broadcaster documentation |
| Platform behavior | Each platform has one stable algorithmic goal | Time-sensitive experiment hypothesis | Dated platform guidance plus account/content-type analytics |
| Platform polish | Reels rewards polish and TikTok rewards rawness | Audience/account hypothesis | Controlled packaging variants and account baseline |
| Depth of field | Shallow is premium; deep is amateur | Rejected as a universal claim | Project visual intent and audience comprehension |
| Digital silence | Absolute silence is inherently unsettling | Contextual continuity risk; intentional silence is valid | Scene intent and listening review |
| Color psychology | A hue reliably creates one emotion | Starting association only | Culture, brand, genre, and real-material preference evidence |
| Hook score | Lexical/position heuristics predict viral potential | Suggestion only; never approval | Post-publish metric objective and baseline comparison |

When a claim is verified:

1. add the source, publication/observation date, scope, and limitations;
2. identify the active handbook or contract rule it supports;
3. add a regression test or experiment template where possible;
4. record when the claim should be rechecked.
